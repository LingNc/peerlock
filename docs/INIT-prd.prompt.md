# PeerLock — 产品需求初步构想 Prompt

> **目标读者**：产品经理
> **用途**：基于此初步构想进行可行性分析、需求细化、交互设计和策划方案输出
> **产品代号**：PeerLock
> **版本目标**：MVP 单向控制版本，架构预留对等模式
> **核心场景**：两位用户之间通过 TOTP 动态验证码互相监督设备使用，防止被控方轻易绕过限制。任何策略修改均需控制方提供动态密码。被控方无法单方面解除限制（包括卸载、强制停止、重启等），除非通过预设的高级逃生手段。

---

## 一、产品核心定位与目标用户

### 1.1 产品愿景
一款 Android 应用，实现**两人之间的对等屏幕时间管理**：双方可以互相施加应用使用限制，任何修改限制的操作都需要对方提供基于时间的一次性验证码（TOTP），从而实现真正意义上的"共同约束"，而非传统的家长单向控制。

### 1.2 MVP 阶段范围
**MVP 仅实现单向控制流**（一个控制端、一个被控端），但底层架构必须预留双向关系存储与多密钥管理能力，确保后续升级为对等模式时**核心加密和验证逻辑无需重写**。

### 1.3 目标用户场景
- 情侣/朋友互相监督减少手机沉迷
- 家长与青少年子女（替代系统级家长控制，因小米账号等问题无法使用）
- 自我管控辅助（一人主动交出控制权，另一人协助监督）

## 二、核心需求与功能边界

### 2.1 防逃避要求（最高优先级）
应用必须防止被控端用户通过**非技术手段的简单操作**逃避限制。具体要求：
- **禁止普通卸载**：用户无法在系统设置中直接卸载
- **禁止强制停止绕过**：即使强制停止管理 App，已暂停的应用仍保持不可用状态
- **重启后限制依然生效**：设备重启不会解除任何已设置的管控策略
- **明确排除的威胁场景**：adb shell 操作、root、恢复出厂设置等不计入防御范围（因操作难度 > 直接询问密码）

### 2.2 核心管控功能
1. **应用使用时长统计与限制**
   - 精确记录每个应用的前台使用时间（使用 UsageStatsManager）
   - 支持设置每日时长上限
   - 支持设置可用时间段（如 20:00-22:00 之外禁用）
   - 支持应用黑白名单

2. **强制应用暂停**
   - 使用 DevicePolicyManager.setPackagesSuspended 彻底暂停指定应用
   - 被暂停的应用图标变灰、无法启动
   - 该状态受系统级保护，不受管理 App 自身存活状态影响

3. **使用数据存储与展示**
   - 本地加密数据库存储详细使用记录（包名、时间戳、使用时长等）
   - 提供按天/周/月的图表查看功能

4. **网络拦截（可选功能，P1）**
   - 使用本地 VPN 服务实现按应用过滤网络访问（借鉴 NetGuard，基于 TUN 接口按应用 UID 过滤）
   - 需注意 Android VPN 的独占性（同一时间只能有一个 VPN 连接），开启本 App 的过滤 VPN 会与其他 VPN 冲突，需提前明确告知用户
   - 可通过 Device Owner 将本 VPN 设为"始终开启"防止手动断开
   - MVP 阶段可暂不实现，优先暂停应用方案

### 2.3 安全验证机制
**所有策略修改操作**（调整时间限制、修改黑白名单、更改可用时段等）和**临时解除限制操作**，均需输入控制方提供的 6 位 TOTP 验证码（30 秒时效），否则不可修改。

**三密钥设计**：
- **设置密钥（Admin Key）**：用于修改管控策略
- **解锁密钥（Unlock Key）**：用于申请临时解除限制
- **销毁密钥（Destroy Key）**：软件内执行永久关闭/解除管控的最高权限密钥
- 三种操作的验证码必须区分，防止误用
- 所有密钥均基于 TOTP（RFC 6238，30 秒窗口，6 位数字），控制方可使用通用验证器 App（如 Google Authenticator）保存种子

## 三、技术架构关键决策

### 3.1 防绕过：Device Owner（设备所有者）
**这是唯一能在不 root 前提下实现防卸载、防强制停止、暂停应用的技术路径。**

**决策要点**：
- 必须让应用成为 Device Owner
- 初始化方式：通过无线 ADB（Android 11+ 的无线调试配对）在应用内引导用户完成一次性设置，无需连接电脑（类似 Shizuku 的无线配对体验）
- 同时提供有线 ADB 命令备用方案，并内置详细图文引导
- 设置后永久生效，重启不影响
- 副作用说明：部分厂商 ROM 可能限制无线调试端口或有额外确认步骤

### 3.2 紧急逃生通道
**必须提供两条逃生路径**，避免设备变砖：

1. **外部 ADB 紧急取消**
   - 在应用界面显示专用 ADB 命令脚本
   - 执行后依次：清除设备所有者 → 解冻所有应用 → 关闭 VPN 锁定
   - 需电脑连接操作（符合"adb 难度大于直接问密码"的安全假设）

2. **应用内超级密钥取消**
   - 使用第三个独立密钥（"销毁令牌" / Destroy Key）
   - 验证后执行完整解除流程
   - 种子仅由控制方极高安全级别保管

### 3.3 安全密钥分发（初始配对）
**核心原则**：被控端的人类使用者不能从通信过程或存储介质中获取密钥明文；被控端设备内可以存在解密后的种子用于 TOTP 校验，但必须依靠 Android Keystore 硬件级保护防止提取。

**推荐实现方案（非对称加密密封传输）**：
1. 被控端（A）应用在初始化时生成 ECC 密钥对（见下方算法选型）
2. 私钥锁定在 Android Keystore 中，完全不可导出，仅应用可调用解密操作
3. 公钥编码为二维码，被控端展示给控制端（B），通过视频通话或当面确认防篡改

**非对称加密算法选型**：
- 首选 ECC 曲线 secp256r1 (NIST P-256)，利用 Android Keystore (API 23+) 的硬件级密钥生成与安全存储，以 65 字节未压缩公钥实现便捷的单次安全配对
- API 10+ 设备引入 Curve25519 (X25519/Ed25519)，作为面向未来的高性能备选，其 32 字节公钥更具优势
- 项目代码需通过适配层支持多曲线，实现平滑扩展
4. 控制端（B）在安全工具中：
   - 生成 TOTP 种子（设置密钥 + 解锁密钥 + 销毁密钥）
   - 生成自己的密钥对
   - 用 A 的公钥加密（种子 + B 的公钥）
   - 用自己的私钥签名
5. 打包为二维码或加密字符串，A 应用扫描后：
   - 用自己的私钥解密获取种子和 B 的公钥
   - 用 B 的公钥验证签名
   - 将种子加密存储，明文从内存释放
   - 保存 B 的公钥，为后续双向安全通信建立信任锚点

**此方案的优势**：
- 一次配对完成种子分发 + 双向公钥交换
- 无需多轮握手
- 为未来双向通信、对等模式直接提供基础

### 3.4 本地安全存储
- TOTP 种子：使用 Android Keystore 加密存储
- 使用记录数据库：使用 Room + SQLCipher 加密
- 密钥材料：不可导出，使用 EncryptedSharedPreferences 保存非敏感配置

### 3.5 时间同步与防篡改
- TOTP 验证允许前后 1-2 个时间窗口容差
- 需要检测系统时间大幅跳变（超过 30 秒），若检测到异常立即冻结所有已暂停应用并进入安全模式
- 需要输入设置密钥方可恢复

### 3.6 恢复机制（MVP 阶段简化）
- 初期不实现脆弱的 6 位纯数字恢复密码（100 万组合存在暴力破解风险）
- 采用**加密种子备份文件**，由控制方保管
- 若控制方丢失令牌，可使用该备份文件配合控制方的一次性恢复码（线下传达）在另一台设备上恢复种子
- 后续可引入服务器辅助恢复

## 六、用户交互流程（MVP 单向模式）

### 6.1 首次启动 — 角色选择
- 用户选择："我需要被管控"或"我要管控对方"
- 根据选择进入对应的配对引导

### 6.2 配对流程
1. 被控端点击"生成配对码" → 展示公钥二维码（含简短配对指令）
2. 控制端选择"扫描配对码" → 扫描后自动生成种子并展示回传二维码
3. 被控端扫描回传二维码 → 自动解密、验证、存储完成
4. 双方界面显示"配对成功"及对方设备标识

### 6.3 日常使用
- **被控端**：查看自己的使用报告，受限应用呈现为灰色，点击"申请解锁"弹窗输入控制方告知的 TOTP
- **控制端**：查看被控端使用报告，修改策略时需要输入自己 TOTP App 生成的管理验证码

### 6.4 交互与 UX 关键点
- 被控端日常使用无感，仅在触发受限应用时弹出提示
- 修改策略界面需清晰说明"此操作需对方的 6 位动态验证码"，并提供输入框
- 任何错误输入须有次数限制（输错 5 次锁定 1 小时）
- 状态栏常驻通知，说明设备处于管理状态（Android 要求）
- 提供使用时长仪表盘，让被控方了解自身使用情况

## 七、架构扩展性要求

- 底层核心模块支持**双向控制关系存储**，数据库设计使用 `role` 字段区分控制方向
- UI 层 MVP 仅展示单向视图，但代码结构允许后续对等模式只需新增另一组管理界面，无需改动安全引擎
- 加密、TOTP 验证、设备策略执行模块均独立，便于单元测试和模块化开发
- 预留与轻量级服务器交互的接口（上报策略、远程修改、日志同步），但 MVP 完全离线可用

## 九、讨论中已达成的关键共识（供 Agent 内部参考，不进入 PRD）

- 普通权限的应用无法满足防卸载、暂停应用的要求，Device Owner 是唯一路径
- adb 初始化虽然略复杂，但在用户配合场景下完全可接受（类比 Shizuku 的无线配对体验）
- 6 位纯数字恢复密码若直接推导种子，存在暴力破解风险（100 万组合），已否决改为备份文件/服务器恢复方案
- 被控端本质上可以接触解密后的种子（在内存中），但依赖 Keystore 硬隔离，在非 root 设备上无法提取，满足威胁模型
- 对等模式的技术基础已通过一次配对完成（双向公钥交换），未来升级主要是 UI 和冲突处理逻辑的工作
